## Proposed, not confirmed by the owner

### For the owner to settle

- The feature promises the `silo` command and MCP tools: does the MCP server ship only where an agent program needs it?
  - Recommendation: Yes: MCP tool descriptions sit in the context of every session, and `silo help` costs nothing until the agent runs it.
- What does Silo put in an agent's context by default: nothing unless turned on, one line pointing to `silo help`, a skill, or tools added just in time by an overseer model (your idea)?
  - Recommendation: One line, in every computer: the loop needs an agent that knows it can fork, and tools that change mid-session break the prompt cache.

### For whoever builds it

- What reaches the agent's context
  - Rule: What Silo injects into an agent's context is the same from turn to turn and placed at the end, so the provider's prompt cache keeps working.
  - Rule: The set of tools Silo exposes does not change within a session.
  - Property: What Silo adds to an agent's context at session start stays under a stated number of tokens.
  - Rule: Silo's agent docs and any skill ship inside each computer, pinned to the installed Silo version, and are never fetched or updated over the network.
  - Rule: Every instruction Silo gives agents answers an observed failure and is backed by an eval, or it is removed.
  - Detail: A setting per computer tells its agent how far to use Silo: as usual, no fork for this, or no Silo instructions at all.
- Commands and calls
  - Rule: A result, a structured answer or an approval request from an agent reaches Silo through an explicit call that the engine validates, never by parsing the agent's output.
  - Detail: Through Claude Code's and Codex's own plugin and hook systems, an approval request or a report to the app fires as a hook and never depends on the agent's memory.
  - Property: The same `silo` command on the same state gives the same output.
  - Detail: `silo help`, a list command and a describe command let an agent find every feature and tell the user about it at the right moment.
  - Detail: One command tells an agent where it is: what this computer is, what it can reach, how to ask for approval, how to fork and merge.
  - Detail: From main, an agent can tell the user what happened and what changed in a fork by reading its events and its diff, which it cannot alter.
  - Rule: Structured output that Silo asks of an agent is flat, with no nested arrays.
  - Detail: Commands accept a partial id.
- Forking by itself
  - Rule: Forking is the easiest path for an agent, since a skill alone gets skipped; whether Silo enforces it is settled in the topic `main-and-forks`.
  - Detail: The agent in main decides by itself when a request is big enough for a fork, picks a model for the task and reports back.
- Agent docs
  - Docs: The first screen of the agent docs says the agent is in a computer it may fork, checkpoint and drop.
  - Docs: The first screen of the agent docs states the loop (fork, work, diff, merge, with status to look around) and where results are read.
  - Docs: The agent docs hold a few short guides that point to commands, each with a worked example: work in a fork, read a diff, show status, ask for approval, request a merge.
  - Docs: The agent docs are one file that fits whole in a context window, generated by a script that removes duplication, and split by task once it grows too big.
  - Docs: The agent docs say how the agent talks to the user, for example that it runs commands itself and never tells the user to run them.
  - Docs: The agent docs tell an agent in a fork to trust what is live in its computer over what it remembers.
- Checks
  - Test: A cheap model that has only Silo's shipped docs forks, checkpoints, diffs and asks for a merge and for access, each in a throwaway computer; every case passes.
  - Test: Each supported agent program completes 'fork this, try X, show me what changed' in one go, without being told to use Silo.
  - Detail: The suite tracks its pass rate and its first-try rate.
  - Test: In each supported agent program, a first message 'hello there' is sent with and without Silo's instructions, and the difference in tokens is under the budget.
  - Test: In evals built from real sessions, an agent given a small task takes the light path: it does not fork, and Silo's instructions do nothing.
  - Test: The schema of every call is given to each supported agent program, and each accepts it.

## From the old code

The old code had it built and driven end to end, about 8,700 lines, and its approach can be reused.

Lessons:
- One loopback port per computer plus a token only that computer holds; the network allows exactly that port.
- The engine puts the shipped program back at each start if an agent replaces or deletes it.
- The peer address is always 127.0.0.1, so only the token tells computers apart; never send the token itself, prove it per nonce and port.
- Any program on the device can connect to the loopback port; on a shared Linux host this is weaker than single-user.
- The earlier /.msb request-file bridge needed holds and cache dropping around checkpoints and did not exist for macOS; it was removed.
- A loopback TCP port has no owner: any account can connect or take it while the engine is down, so the token is the identity.
- Keep a port that is no longer a computer's bound with an accept-and-close listener until the computer restarts without it.
- Device-only tools (up, ssh_name, request_open) are hidden inside a computer; secrets and export/import are never MCP tools.
