## Findings

- **Two host-shared mounts beyond the expected ones.** The guest also has `/.msb`
  (virtiofs, **read-write**, source `msb_runtime`, the runtime's own share) and
  `/opt/silo/lcu` (read-only). The canary was not reachable through either, but a
  writable share from the Mac deserves its own review; it is listed as a follow-up.
- **Host DNS.** TCP port 53 on the host side answers: the DNS forwarder, the one host
  service the network profile allows.
- **Not covered by this run.** `github-scope` (GitHub not connected) and the
  cross-user socket attempt (`--other-user`). Both remain to be run.

## Run notes

- The first attempt returned `error` for the three secret scenarios
  (`secrets.save: credential_access_denied`): Keychain items from an earlier Silo Dev
  build refused this ad hoc–signed one. `engine.credentials.repair` fixed access and
  every scenario was run again; the table is from that second run.
- The engine was a local debug build. Two packaging gaps had to be worked around on
  the test Mac and are tracked separately: debug app builds skip embedding the engine,
  and `embed_engine.py` copies only `silod`, not the `msb` runtime and `libkrunfw` it
  loads from its own bundle.
- The raw evidence (`.json`) is not published: it contains the test Mac's public and
  LAN addresses.
