# S2 spike: rebuild a Linux computer on the newest image, keeping its data

Run on 2026-11-10 with the bundled `msb` 0.7.6 (patched build, `app/SiloUI/src-tauri/binaries/msb-aarch64-apple-darwin`),
a private runtime home (`~/.s2/home`), and sandboxes named `e2e-s2-*`. The "old" computers were made from the
Preview image `ubuntu-24.04-v4`, the "new" ones from the Dev image `ubuntu-24.04-v5` (both imported read-only
from `~/Library/Application Support/org.silo.{preview,dev}/guest-image/`). No Silo or Silo Dev engine or app was
started, stopped or called. Everything below was run unless marked **(read)**. Scripts used are in
[`S2-scripts/`](S2-scripts/). Hardware: Apple silicon Mac, APFS (cloning works). Linux hosts were not tested.

## Answers

| # | Question | Answer |
| --- | --- | --- |
| 1 | Where is the workspace disk, what refers to it? | `<runtime home>/sandboxes/<name>/owned-volumes/workspace_<hash>/disk.raw`. `<hash>` (`c52ddf65`) is a hash of the guest path `/workspace` only: it is the same for every computer and every size. The file is a plain sparse raw ext4 (1 GiB apparent, 4.2 MB used when empty). The saved config says only `{type: Owned, guest: /workspace, storage: {kind: disk, capacity_mib}}`: **no path, no hash**. The runtime checks that `disk.raw` exists, is a regular file, and has exactly `capacity_mib` bytes. After the first start there is `.disk-owner` (a lock file) and `runtime/owned-disks/workspace_<hash>/disk.json`: a journal with a random `volume_id` and the list of layers (relative paths, format, `integrity_root`). **After any checkpoint, restore or compaction the disk is no longer one file**: it is `disk.raw`/`sealed-000.raw` plus `head_*.qcow2`/`writable.qcow2`/`sealed-001.qcow2` layers (and a `.compact-*` folder after `--compact`), listed in `disk.json`. `sealed-000.raw` is a hard link shared with the snapshot store. The database (`sandbox`, `sandbox_rootfs`, `volume`, `volume_attach`) holds nothing about the owned disk. |
| 2a | Adopt-disk | **Works, supported, 0.27 s.** Create the new computer with `--mount-disk <clone of old disk.raw>:/workspace:format=raw,fstype=ext4` instead of `--mount-owned`, then `msb adopt-disk <new>` (optionally `--source`). Boots, data intact, checkpoint and restore work afterwards. Needs a **single raw ext4 file** as the source (a computer without checkpoints has one; a chained disk has none); on an already-owned disk it does nothing. The size is taken from the file. |
| 2b | Replace the file on the host | **Works** (APFS clone, 0.002 s). New computer created with its own empty disk, started once (journal exists), stopped, `disk.raw` replaced: boots, zero differences in a 2055-entry manifest, checkpoint, restore and `snapshot verify` work afterwards. For a **layered** disk, replace the whole `owned-volumes/<id>/` folder and the `layers` array of `disk.json` (keep the new computer's `volume_id`): also works, including onto a computer that came from `msb restore` (the recipe-fork case). Rules found by trial below. |
| 2c | Other ways | `msb restore` restores a whole computer (root + workspace) from one snapshot; no option takes only the workspace. A named disk volume (`msb volume create --kind disk`, `--mount-named`) would survive its sandbox, but today's computers use `--mount-owned`, and a mount cannot be removed again (`msb modify` has no mount option). `msb modify --compact` merges sealed layers into a qcow2, never into a single raw. |
| size | Must the size match? | **Yes, exactly, at start**: a 1 GiB file in a 2 GiB computer fails with "owned volume /workspace chain identity or capacity differs from its configuration". Growing is easy: `truncate -s 2G disk.raw` before the start, then `resize2fs /dev/vdc` online in the guest (1 GiB to 2 GiB verified, data intact). Shrinking was not tried (needs an offline `e2fsck` + `resize2fs`). |
| 3 | Home folder | `msb exec A -- tar … \| msb exec B -- tar …` **works and keeps** owners, modes, setuid, hard links, symlinks (also dangling), xattrs, mtimes, sparse files (with `--sparse`), unicode names, a mode-000 file, a numeric foreign owner. It does **not** carry the Unix socket (tar skips it; fine) and is **slow in one direction**: 979 MB / 50,000 files took **1 min 41 s** (guest-to-host `exec` output is about 10 MB/s; host-to-guest input is about 190 MB/s). **Better: tar inside the guest to a file, `msb cp` it out and in, untar**: 1.15 GB in **9 s** (tar 3.2 s, cp out 0.8 s, cp in 2.2 s, untar 2.6 s), identical result. Needs free space for the tar on both root disks. A read-only mount of a clone of the old root disk (`--mount-disk … :ro`) also copies the home in 3.4 s, but the mount stays in the new computer's config for good, so it was rejected. |
| 4 | Identity | Listed below. A rebuilt sandbox can carry the **old name and the old `silo.machine-id`**: `msb rename` (0.09 s) plus `msb modify --label silo.machine-id=…` both work on stopped computers. Then every store keyed by id or by name keeps pointing at the right computer and almost nothing is re-pointed. Reusing promote's rename-into-place covers the swap and the journal/undo shape, not the carrying of host-side files or the workspace. |
| 5 | Replace the root disk in place | **Works, but by editing the runtime's private SQLite**: in `sandbox.config` change `image`, `manifest_digest` and the `org.opencontainers.image.*` labels; set `sandbox_rootfs.manifest_id`; replace `upper.ext4` by a pristine one (an APFS clone of a never-booted new computer's). The computer keeps its row, name, labels, workspace disk (untouched), network, secrets. Booted the new image, root changes gone, workspace marker kept, checkpoint/restore work, and restoring a pre-swap checkpoint brings the old image back. More fragile than a new sandbox (private schema, and a layered root needs `root-disk.json` rewritten); worth doing only as a small runtime patch. |
| 6 | macOS | Read only, below: possible in outline, blocked mostly by the cost of a new template and the keychain. Not a first step. |

## 1. The workspace disk on the host

```
$ msb create <image> --name e2e-s2-old --root-disk 4G --mount-owned /workspace:kind=disk,size=1G … --no-start
sandboxes/e2e-s2-old/upper.ext4                                    4294967296 bytes (3.6M used)   root disk
sandboxes/e2e-s2-old/owned-volumes/workspace_c52ddf65/disk.raw     1073741824 bytes (4.2M used)   workspace
# same name workspace_c52ddf65 for a 2 GiB disk and for every other sandbox
$ sqlite3 db/msb.db "select * from sandbox_rootfs; select * from volume; select * from volume_attach"
1|1|3|erofs|ext4|…|managed|          (volume tables are empty: owned disks are not catalogued)
```

After the first start (`runtime/owned-disks/workspace_c52ddf65/disk.json`), no checkpoint yet:

```
{"schema":"microsandbox.runtime-owned-disk/1","device_id":"workspace_c52ddf65","volume_id":"vol_ab5a…",
 "launch_base":"owned-volumes/workspace_c52ddf65/disk.raw","generation":0,
 "layers":[{"layer_id":"layer_b529…","path":"owned-volumes/workspace_c52ddf65/disk.raw","format":"raw","integrity_root":null}]}
```

After a snapshot, a start and a second snapshot (`generation: 2`): the base gets `integrity_root: blake3:…`,
and `head_<id>.qcow2` layers are added. After `msb restore`: `sealed-000.raw` (hard-linked ×3 with the snapshot
store) + `writable.qcow2`. After `msb modify --compact --disk /workspace`: layers inside `.compact-XXXX/`.
`runtime/root-disk.json` has the root disk's layers with **absolute** paths (`msb rename` rewrites them; checked).

The runtime's validation (`sdk/rust/lib/runtime/owned_volumes.rs`, **read**) requires: no symlinks, the folder
exists, and either a journal (then its `virtual_size` must equal the configured capacity) or a regular
`disk.raw` of exactly `capacity_mib`.

## 2. Giving a new computer an existing workspace disk

Test data in the old computer (v4 image, silo account set up with the engine's own `working-account.sh/.py`):
`/home/silo` 979 MB, 50,014 files (500 directories of 100 × 20 KB random files, plus links, a fifo, a socket,
setuid, mode 000, a root-owned file, a file owned by 1234:4321, xattrs on a file and a directory, a 50 MB sparse
file, unicode name, `.claude.json`); `/workspace` 104 MB, 2,055 entries (a 100 MB file, a setgid directory, a
root-owned file, a symlink, an xattr). `tree` installed with apt (root-disk change). `manifest.py` lists every
entry with mode, owner, size, mtime, link count, md5 (small files), link target, xattrs; `verify.sh` diffs it.

### (a) `adopt-disk`

```
$ cp -c old/owned-volumes/…/disk.raw ~/.s2/stage/a-ext.raw                 # 0.003 s, no space used
$ msb create <v5> --name e2e-s2-a … --mount-disk $HOME/.s2/stage/a-ext.raw:/workspace:format=raw,fstype=ext4 --no-start
$ msb adopt-disk e2e-s2-a                                                  # 0.27 s
Adopted /workspace as sandbox-owned storage
mounts: [{'type': 'Owned', 'storage': {'capacity_mib': 1024, 'kind': 'disk'}, …}]
$ msb start e2e-s2-a      ->  /workspace is 104M used; first boot has no silo account yet
$ account.sh e2e-s2-a     ->  0.4 s; then verify.sh:
2054c2054  < rootfile|0o100644|0:0|…   > rootfile|0o100644|1001:1001|…       (only difference)
```

The only difference is the engine's own account setup running `find /workspace -xdev -exec chown -h silo:silo`,
which turns root-owned files into `silo` files. A rebuild that does the account setup **before** the swap
(variant b) avoids it.

Checkpoint and restore after the move: `snapshot create ck1`, start, `rm big.bin`, write a file, `snapshot create
ck2`, `msb rm`, `msb restore g-a:ck1 --name e2e-s2-a …` (0.38 s): `big.bin` is back (md5 equal), the new file gone,
`working-account.json` present.

### (b) Replace the file

```
# new computer with its own disk, one real boot, account set up, stopped
$ mv owned-volumes/workspace_c52ddf65/disk.raw …/disk.raw.orig ; cp -c <old disk.raw> …/disk.raw ; msb start …
-> data present, verify.sh: lines old=2055 new=2055 difflines=0     (rootfile still root-owned)
$ snapshot create ck1 / start / change / snapshot create ck2 / rm / restore ck1  -> pre-change data, difflines=0
```

Rules found:

| Trial | Result |
| --- | --- |
| Swap before the new computer's first start (no journal yet) | Works (`c1`). |
| Swap after a checkpoint already exists on the new computer, base layer replaced, `head_*.qcow2` left | Boots and shows the data. **Unsafe**: the head sits on a different base, and start does not verify the integrity root. Do not do it. |
| Leave `disk.raw.orig` next to `disk.raw` before the first start | `invalid config: owned disk has chain storage but its authoritative journal is missing`. The folder must hold only the disk's own files. |
| 1 GiB disk in a 2 GiB computer | `chain identity or capacity differs from its configuration`. |
| The same file grown with `truncate -s 2G`, then `resize2fs /dev/vdc` in the guest | Boots; `df` 2.0G; data intact. |
| Old disk **with** checkpoint layers (`sealed-000.raw`, `sealed-001.qcow2`, `writable.qcow2`): clone the whole folder, copy the `layers` of the old `disk.json` into the new one, keep the new `volume_id` | Boots, 2058/2055 entries as expected (3 files added after the restore), `md5sum -c` ok, then snapshot, change, restore: ok. |
| Same, onto a computer produced by `msb restore g-b2:ck1` (what a recipe fork is), then `snapshot create` and `snapshot verify` | Boots; `Verification: verified (msb-file-merkle-blake3-v1 …)`. |
| `msb snapshot create … --group <old group>` from the rebuilt computer | Accepted; the group reports `UnknownAncestry` for the old head. A new group also works. |

`swap-workspace.py` is the whole surgery (staged `cp -c -R`, old folder moved out of `owned-volumes/`, journal
rewritten atomically).

## 3. The home folder

```
# pipe, 979 MB, 50,014 files (home.manifest vs the target: only the socket missing)
$ time ( msb exec old --no-tty --user root -- tar -C /home -cpf - --xattrs --acls --numeric-owner --sparse silo \
       | msb exec new --no-tty --user root -- tar -C /home -xpf - --xattrs --acls --numeric-owner --same-owner )
  1:41.56 total
# where the time goes
guest -> host through `exec` output, 95 MB      8.96 s   (about 10 MB/s)
host -> guest through `exec` input, 95 MB       0.54 s   (about 190 MB/s)
# file route
tar in guest to /tmp/home.tar (1.15 GB)         3.2 s
msb cp old:/tmp/home.tar → host                 0.8 s
msb cp host → new:/tmp/home.tar                 2.2 s
tar -x in the new computer                      2.6 s    (total about 9 s)
```

Result of the file route (`verify.sh e2e-s2-h1 home`): 50,523 of 50,524 entries identical in mode, owner,
numeric owner 1234:4321 and root-owned kept, setuid bit, directory 700, hard-link count 3 and the same inode,
dangling and relative symlinks, xattrs (`user.note`, `user.dirnote`), mtimes, sizes. Without `--sparse` the 50 MB
sparse file is stored in full (tar is 1.15 GB instead of 0.86 GB). The tar needs room on both root disks: my first
attempt put the tar on the 1 GiB workspace disk and was silently truncated (`Unexpected EOF`); the root disk
(`/`, a 4 GiB upper layer) must hold the tar and, in the new computer, the tar plus the unpacked home, so a home
of up to about 1.8 GiB fits; bigger homes need the slow pipe or chunked tars.

The account must exist **before** the home arrives: `working-account.py` refuses a `/home/silo` that exists without
its account ("The silo home folder exists without its account") and otherwise creates the account and chowns
`/workspace`. So the order is: first boot, account setup, then extract over the new home (the image's three skeleton
dotfiles are replaced by the old computer's).

Alternative tried: create the new computer with `--mount-disk <clone of old upper.ext4>:/mnt/oldroot:format=raw,fstype=ext4,ro`
(option spelling: `ro`, not `readonly`). The old home is then at `/mnt/oldroot/upper/home/silo` and
`cp -a` of the 979 MB takes 3.4 s with owners kept. Rejected: the mount cannot be removed later and would stay in
the computer's saved configuration.

## 4. Identity: what ties to a computer's name and id (read)

What the engine keeps, from `runtime/mod.rs`, `runtime/checkpoints.rs`, `changes/promote/linux.rs`, `editor.rs`,
`ssh_access.rs`, `network.rs`, `secrets.rs`, `computer_tree.rs`, `changes/store.rs`, `computer_use.rs`,
`runtime/storage.rs`, `recipes/`:

| Item | Keyed by | Lives in | In a rebuild that returns the old name and id to the new sandbox |
| --- | --- | --- | --- |
| Computer entry (cpus, memory, storage GiB, desktop, runtime kind) | id (name is a field) | `metadata` inventory | unchanged |
| `silo.machine-id`, `silo.managed`, `silo.workspace-storage-gib`, `silo.runtime-storage-gib`, `silo.github-protocol` labels | label on the sandbox | runtime config | set at create; `msb modify --label` (stopped) works for the id |
| Checkpoint record, lineage group, pending restore, desired network policy, desired environment, quiet record | id (`checkpoints/<id>.json`) | engine | unchanged; the old checkpoints stay in the old group and still restore (to the **old image**, which is the undo) |
| Fork tree link, promote journal | id (`changes/store` `computers/<id>/`) | engine | unchanged |
| Computer-use policy and observed state | id | engine | unchanged |
| Storage maintenance record | id (`storage-maintenance/<id>.json`) | engine | unchanged |
| SSH: client key, `<id>.conf`, `<id>.known_hosts`, `<id>.authorized_keys` (managed access) | id | engine `ssh/` | unchanged |
| SSH **host key** the client pins | **sandbox folder name** | `<runtime home>/sandboxes/<name>/ssh/host_ed25519` (host side, not in the guest) | **must be copied** to the new sandbox's folder, or every SSH client sees a changed host key |
| SSH entry's reach (`ProxyCommand` through the name) and listener per computer | name | engine | unchanged once the name is back |
| Published ports and their forwards | name (`network.json`, `export_mappings` / `replace_mappings`) | engine | unchanged once the name is back; the live forwards need a start |
| Secrets: assignments, revision, verified-start counter | name (`secrets.rs`, `fork_assignments(source, target)`) | engine | unchanged; the secret **values** are passed again at create (`--secret`), as Restore does |
| GitHub profile and access state | name (in memory: `forget_github_state(home, name)`) | engine | forget both names after the swap, as promote does |
| URL proxy routes | name, tagged by id | engine memory | `forget_computer_id`, as promote does |
| Network policy, TLS, ports in the sandbox | sandbox config | runtime | passed at create from `desired_network_policy` (`current_network_args`) |
| Spool for the guest client, logs, metrics | sandbox folder name | `sandboxes/<name>/…`, runtime | rename moves the folder; a new sandbox starts with empty logs |
| Recipe (name, hash, text) | id (planned: stored with the computer) | engine | hash includes the image string, so the newest image gives a **new hash and a new build**; the hidden build computer is cached by hash |
| Account record, components receipt | the guest root disk | `/var/lib/silo/…` | written fresh by the setup on the new root disk |

So the important choice is **who gets the old id**. Promote keeps ids with their computers and swaps only names
(the id aliases of SSH entries are re-pointed). A rebuild instead gives the new sandbox the old name **and the old id**
(`msb modify --label silo.machine-id=…`) and gives the old sandbox a fresh archive id and name. That needs no
re-pointing of id-keyed stores. Promote's pieces that still apply: the rename of two stopped sandboxes
(`rename_sandbox`), `forget_name_state`, `forget_computer_id`, the journal with `apply`/`revert` per step and the
rule that a sandbox is identified by its label, never by its name. Promote's `ports_apply`/`repoint_id_alias` are not
needed. What promote does not cover: creating the new sandbox on a new image with the old arguments, moving the
workspace disk, the home folder, the SSH host-key folder, the checkpoint taken first.

## 5. Replacing the root disk in place

```
# e2e-s2-e6: v4 computer, /workspace/pre and /etc/e6 written, then:
$ msb snapshot create ck-pre --from-sandbox e2e-s2-e6 --group g-e6 --integrity
$ python3 swap-root.py e2e-s2-e6 fresh-config.json e6-config-after.json    # image, manifest_digest, OCI labels from a fresh v5 computer
$ cp -c <fresh v5 computer>/upper.ext4 e2e-s2-e6/upper.ext4.new && mv -f … upper.ext4
$ sqlite3 db/msb.db "update sandbox set config=cast(readfile('…') as text) where id=N;
                     update sandbox_rootfs set manifest_id=1 where sandbox_id=N;"      # manifest 1 = the v5 image
$ msb start e2e-s2-e6   ->  /workspace/pre present, /etc/e6 gone, image reference v5
$ msb restore g-e6:ck-pre --name e2e-s2-e6u …  ->  /workspace/pre and /etc/e6 present, image reference v4   (undo)
```

The config diff between a v4 and a v5 computer is only: `image.Oci.reference`, `manifest_digest`, the four changed
`org.opencontainers.image.*` labels (description, revision, source, version), the name and `silo.machine-id`. `readfile()` stores a BLOB and breaks the row
(`mismatched types … BLOB`); `cast(… as text)` is needed (I hit this once and repaired the row). After the swap a
checkpoint/restore cycle keeps the v5 image.

Assessment: simplest for identity (nothing moves, the row, name, id, labels, network, secrets, workspace stay), and
the undo is the engine's existing restore. But it writes the runtime's private schema (S1 reached the same
conclusion for network rules), a restored computer's root is `upper.ext4` + `upper-restore-*.qcow2` listed in
`root-disk.json`, which would have to be collapsed to a fresh single layer, and the home must still be taken off
the old root disk first. As a small runtime patch (`msb modify --rebase-image <ref>`: stopped only, new
`upper.ext4`, journal reset, config and manifest row updated under the lifecycle guards, mirroring the adopt-disk
patch) it would be the cleanest. As engine code that edits SQLite, no.

## 6. macOS computers (read only)

`templates.rs`: a template is a stopped, finished computer kept as APFS clones of its disk, auxiliary storage and
hardware model in `macos-templates/<build>-<setup version>[-<computer use version>]`, with the guest-access secrets
of the computer it came from. A new computer is a `clonefile` copy with a new MAC and machine identifier, a rekeyed
account (`run_template_rekey`: new password hash, auto-login, login keychain cleared) and a personalization of two
boots. `offline_setup.rs::with_data_volume(disk, work)` attaches a **stopped** computer's disk on the host
(`hdiutil`), mounts its Data volume and runs `work(mount_path)`, so `/Users/silo` of the old and the new disk can be
copied on the host without booting either. One disk holds the system, the apps and the home.

"Rebuild on the newest template, keep `/Users/silo`" would be: (1) pick the newest template (a newer macOS build
or setup version); (2) make a copy (existing `copy` flow); (3) with both stopped, `with_data_volume` twice and copy
`/Users/silo` with `ditto`/`rsync -aHE` (xattrs, ACLs, flags, resource forks); (4) swap names and records like a
promote (`macos_computers/ports.rs` has `export_mappings`/`replace_mappings`, `ssh_alias.rs` is keyed by id).

What blocks it:

- **A newer template is rare and expensive**: a changed base or a new macOS build is a full install from a restore
  image plus provisioning (hours); there is no "newest template" to move to on most days.
- **The login keychain** is encrypted with the account password; the template flow generates a new password per copy
  and clears the keychain. Copying the old `~/Library/Keychains` would not unlock. The rebuild would have to give the
  copy the **old** password (the rekey takes an account) and keep the old keychain, or lose saved logins.
- **Everything outside `/Users/silo`** (Homebrew in `/opt/homebrew`, `/Applications`, `/usr/local`, launch daemons) is
  not carried; macOS computers have no recipe to replay, so installed tools are lost unless copied by path.
- Per-user privacy grants (TCC) and computer-use setup depend on the install; they must be re-established by the
  provisioning of the copy, not copied.
- A disk can only grow; a grown old disk needs a grown copy.
- The Data volume mount is exclusive to the host while attached, so neither computer may run during the copy.

## 7. The prototype

`S2-scripts/rebuild.sh <old> <new>` runs the whole sequence below by hand. Two runs: the first (timings broken
by a shell bug) produced the final state checked afterwards, the second gave the timings.

```
 2 checkpoint old (disk, --integrity)         1.1 s
 3 create new (v5, same args)                 0.04 s
 4-5 first boot + account setup               1.6 s + 0.4 s
 7 swap workspace (APFS clone, journal)       < 0.1 s
 9 tar of 979 MB home in old                  3.2 s
10 cp to host                                 0.8 s
12 cp into new                                2.2 s
13 extract in new                             2.6 s
14 recipe replay (apt-get install tree)       3.6 s    (a real recipe is minutes; cached by hash)
15 stop both                                  0.3 s
16 rename old → <name>-undo, new → <name>; relabel machine-id on both   < 0.1 s
```

Final state, checked: `e2e-s2-old` is on `ubuntu-24.04-v5` with label `silo.machine-id=e2e-s2-old`, `tree` present
(replay), home identical to the old tree (50,523 of 50,524 entries, socket missing), workspace identical (2,054 of
2,055 entries; the one difference is the mount root directory's mtime, and the root-owned file kept its owner because
the account was set up before the swap), `e2e-s2-old-undo` still on v4, started and showed workspace and home.

## Cleanup

All `e2e-s2-*` sandboxes, snapshots, the staged files and `~/.s2` (private runtime home, imported images, signed
copy of `msb`) were removed at the end.
