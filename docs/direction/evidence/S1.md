# S1 spike: channel and network policy on the existing runtime rules

Run on 2026-11-10 with the bundled `msb` 0.7.6 (`app/SiloUI/src-tauri/binaries/msb-aarch64-apple-darwin`,
patched build), a private runtime home, the Dev guest image `ubuntu-24.04-v5`, and sandboxes named
`e2e-s1-*`. No Silo or Silo Dev engine or app was started, stopped or called. Everything below was
run; the places that were only read are marked **(read)**.

## Answers

| # | Question | Answer |
| --- | --- | --- |
| 1 | Does `allow@host:tcp:<P>` give the guest exactly one gateway port? | **Yes.** The guest reaches a Mac listener on 127.0.0.1:P at `host.microsandbox.internal` (IPv6 `fd42:6d73:62:N::1`) and at its IPv4 gateway; port P+1, the Mac's sshd (22) and 127.0.0.1 inside the guest are refused (RST). A sandbox without the rule is refused on P. The Mac-side peer is always `127.0.0.1:<ephemeral>`, the same for every computer, so identity must come from the token. |
| 2 | Can rules of an existing sandbox change? | **Not through `msb`.** `msb modify` has no network option (stopped or running). Supported way: stop, snapshot, remove, `msb restore … --net-default-* --net-rule …` under the same name (what the engine's Restore already does); about 1.2 s for an idle 1 GiB computer, a memory restore keeps processes but resets TCP connections through the gateway. Editing the runtime's SQLite `sandbox.config` while stopped also works, but it is unsupported. A running sandbox ignores an edit until it restarts. |
| 3 | Checkpoint, restore, fork, export | A restore **resets the policy to the runtime default unless every rule is passed again**; passing different rules replaces them, so a fork can get its own port (disk and memory restore both verified). The engine already rebuilds the arguments from `desired_network_policy`, and `host:tcp:P` goes through its generic branch unchanged. **Hostname rules do not**: `current_network_args` only accepts `destination.group` **(read)**. `restore` has **no `--net-strict`**, so a restored or forked computer is always strict (see 4). Export: a host port rule does **not** make export or import refuse (verified with the engine's own functions); a hostname rule does only when `strict=false` (fix below). |
| 4 | Allowlist | **Works at create, with one change: `--net-strict=false`.** With `strict=true` (what Silo passes today) HTTPS to a hostname-allowed host fails unless the host is one a secret covers (GitHub). With `strict=false`: allowed host works, other hosts and direct public IPs fail, `*.suffix` works (apex too), `allow@dns` is needed to resolve names. See the details below. |
| 5 | `--vsock` | **Works.** `--vsock <unix socket>:5000` is accepted by `create` and `restore`; the guest connects with `AF_VSOCK` to CID 2 port 5000 and reaches the Mac's Unix socket (5 of 5). Export refuses a non-empty `vsock` **(read)**. |
| 6 | macOS and containers | The gateway's init `policy` is a `microsandbox_network` `NetworkPolicy` in the runtime's saved JSON shape, so it accepts group `host` with a port and `domain`/`domain_suffix` rules. The name `host.microsandbox.internal` is answered by the same DNS forwarder. It never calls `.strict(false)`, so it is strict (the default), like the restore case. **(read)** |
| 7 | Guest `silo` | **Builds** in 36 s from clean with `scripts/build-guest-silo.sh` (zig as C compiler); 12.7 MB static aarch64 musl ELF; runs in the guest (`silo 0.1.0`). Plain `cargo build --target aarch64-unknown-linux-musl` fails: `ring` needs `aarch64-linux-musl-gcc`. Only `ring` (through rustls and reqwest) needs a C compiler. |

## Setup (so it can be repeated)

Mac listeners: `127.0.0.1:47311` (banner, logs peer), `47312`, `47313`. The guest probe is a Python script that
connects and reads the banner (`CONNECT_OK … banner=…` or `FAIL ConnectionRefusedError:111`).

## 1. Gateway port rule

Grammar, tried against `create`:

| Rule string | Result |
| --- | --- |
| `--net-rule allow@host:tcp:47311` | Accepted. Saved as `{"destination":{"group":"host"},"ports":[{"start":47311,"end":47311}],"protocols":["tcp"]}`. With no `--no-net` and no default flags the runtime **appends** `allow@dns` (host:53 udp+tcp) and `allow@public`, giving `[host:47311, host:53, public]`, default egress deny, ingress allow. |
| `--net-rule allow@host:47311` | Refused: "`47311` is a port, not a protocol; did you mean `host:tcp:47311`?" |
| `--net-rule allow@host.microsandbox.internal:tcp:47311` | Accepted but saved as a `domain` rule, not the gateway group. Do not use. |
| `--net-rule allow:egress@host:tcp:47311` | Accepted, same as the first (this is the form `current_network_args` writes for restore). |
| `--no-net --net-rule allow@host:tcp:47311` | Exact set: `[host:47311]`, egress deny, ingress deny. |
| `--net-default-egress deny --net-rule allow@dns --net-rule allow@host:tcp:47311 --net-rule allow@public` | Exact set, ingress stays allow. |

`github-network-default.json` is what `msb create` produces with no `--net-rule`: default egress deny,
ingress allow, rules `[allow host:53 (udp,tcp), allow public]`. Engine `current_network_args` writes it back at
restore as `--net-default-egress deny --net-default-ingress allow --net-rule allow@dns --net-rule allow@public`.

Probe, sandbox `a` (rule `allow@host:tcp:47311`) against sandbox `b` (no rule), from inside each guest
(`q1-probe` output, trimmed). Sandbox `b`'s IPv4 gateway is `172.16.0.9`, `a`'s is `172.16.0.5`: the address
is per computer, the name is stable.

```
a  host.microsandbox.internal:47311   CONNECT_OK fd42:6d73:62:1::1 banner='hello from mac listener 47311'
a  172.16.0.5:47311                   CONNECT_OK
a  fd42:6d73:62:1::1:47311            CONNECT_OK
a  host.microsandbox.internal:47312   FAIL ConnectionRefusedError:111      (P+1)
a  172.16.0.5:22                      FAIL ConnectionRefusedError:111      (Mac sshd is listening on 22)
a  127.0.0.1:47311                    FAIL ConnectionRefusedError:111      (guest loopback, nothing there)
b  host.microsandbox.internal:47311   FAIL ConnectionRefusedError:111
```

Listener log: `peer=('127.0.0.1', 60239)`, always `127.0.0.1` with an ephemeral port. A restored computer
`c` with rule `…:47313` reached 47313 and was refused on 47311, 47312 and 22. The closed set
(`--no-net --net-rule allow@host:tcp:47311`, no `allow@dns`) reached 47311, refused 47312 and public IPs,
and `getent hosts example.com` returned nothing; `host.microsandbox.internal` still resolves from `/etc/hosts`.

## 2. Changing rules later

- `msb modify --help`: options are resources, env, labels, workdir, secrets, `--dry-run`, `--next-start`,
  `--restart`. No network option. `msb modify … --net-rule x` fails ("unexpected argument").
  `msb start` and `msb restart` take no network option either.
- **Restore in place** (what `checkpoints.rs` Restore does, same name):

  ```sh
  msb snapshot create ck3 --from-sandbox e2e-s1-a --group g-a --full --guest-flush required --integrity
  msb stop e2e-s1-a; msb rm e2e-s1-a
  msb restore g-a:ck3 --name e2e-s1-a --cow-mem --label … --env … --secret … \
      --net-default-egress deny --net-default-ingress allow \
      --net-rule allow@dns --net-rule allow@host:tcp:47312 --net-rule allow@host:tcp:47315 --net-rule allow@public
  ```

  About 1.2 s end to end for an idle 1 GiB computer. The memory restore kept a background `sleep` (same pid)
  and the policy was replaced (`[53, 47312, 47315]`). A guest TCP connection held through the gateway was
  reset (`ConnectionResetError`, then `BrokenPipeError`), so the in-guest client must reconnect. A disk
  restore of a stopped computer replaced the policy the same way (`msb restore g-a:ck1 --name e2e-s1-a …`,
  ~0.35 s). Costs: one extra snapshot in the lineage (the engine names it "Before restore"), a memory
  snapshot sized by the computer's RAM when it was running, a cold boot if restored from disk.
- **Runtime database** (unsupported): while stopped, rewriting `sandbox.config` in `$MSB_HOME/db/msb.db`
  (add the rule to `network.policy.rules`, then `msb start`) was honoured at the next start (reach 47311
  after the edit). The same edit on a running sandbox changed nothing until stop and start. This depends on
  the runtime's private schema; keep it as a last resort, not a plan.
- The patch `microsandbox-restore-policy-0.7.6.patch` adds `--net-default-egress/ingress`, labels, env and
  secrets to `restore`; it adds nothing to change a created sandbox.

## 3. Checkpoints, forks, exports

Restore, as the engine runs it, with and without network arguments (`policy` printed from `msb inspect`):

```
restore g-a:ck1 --name e2e-s1-c            (no network args)  -> rules [host:53, public]   (source's port rule is gone)
restore g-a:ck1 --name e2e-s1-c … --net-rule allow@host:tcp:47313 …
                                             -> rules [host:53, host:47313, public]; reaches 47313, refused 47311/47312/22
restore g-a:ck2 (memory) --name e2e-s1-d --cow-mem … allow@host:tcp:47311 …
                                             -> reaches 47311 only
```

So a fork gets a different port by building its argument list from a policy whose channel rule has the
child's port. In `checkpoints.rs`: `fork.desired_policy` is copied from the source (line ~2469) and
`current_network_args` turns it into arguments (line ~1714); `running_child_matches(..., &policy)` compares the
observed policy afterwards. The channel rule is a `group: host`, one TCP port, so `current_network_args` already
writes `allow:egress@host:tcp:<P>` for it **(read, and the token was accepted by `create`)**. What must change:
the fork path rewrites the port in the copied policy before it builds arguments and before the match check.
Imports start from `desired_network_policy = deny / deny / []` (`checkpoints.rs` ~1583), so the engine adds
the computer's own channel rule when it first starts the imported computer.

`current_network_args` fails with "A current network destination is unsupported" for any rule whose
destination is `domain` or `domain_suffix` **(read)**; it must learn both before an allowlist computer can be
restored or forked: `domain` -> `allow:egress@example.com:tcp:443`, `domain_suffix` -> `allow:egress@*.example.org:tcp:443`
(both tokens verified accepted by `create`).

Export (`backup.rs`). `network_uses_host_files` looks only at TLS certificate files, so no rule trips it. The
export path resets `policy`, `secrets` and `ports` to the deny profile and then compares everything else with
`guest/github-network-default.json` (`portable_export_network`, then `validate_snapshottable_config`). I ran
those two functions on the real `msb inspect` configs (a throwaway test, source in the appendix; the extra keys
`external_mount_policy` and `snapshot_parent` that 0.7.6 reports are removed first):

```
q control: default computer, no rules ........ live validate ok          export ok  validate after reset ok
o open + host:tcp:47311 (fresh) .............. live validate refuses    export ok  validate after reset ok
p deny default + host port + hostname rule ... live validate refuses    export ok  validate after reset ok   (strict=true)
i closed + host port ......................... live validate refuses    export ok  validate after reset ok
e/h allowlist, hostnames, strict=true ........ live validate refuses    export ok  validate after reset ok
f allowlist, hostnames, strict=false ......... live validate refuses    export REFUSES: "custom network strict settings"
a open + host port, after a memory restore ... export REFUSES: "custom network interface settings" (unrelated to rules; see below)
```

"Live validate refuses" is how the code is meant to work (exports reset the network first). So:

- A `host:tcp:P` rule never makes export or import refuse.
- `strict=false` does: `portable_export_network` decides `strict_is_inert` on the original policy (it has hostname
  rules) and keeps `strict=false`. Fix: reset `strict` to the profile's value together with `policy`.
- A computer restored from a **memory** checkpoint reports a pinned `interface` (address, MAC) in its network;
  this makes the export check refuse it. It does not depend on the rules, and I did not check whether the engine
  clears it elsewhere.

## 4. Allowlist

Allowlist set used: `--no-net --net-rule allow@dns,allow@example.com:tcp:443,allow@*.python.org:tcp:443,allow@host:tcp:47311`
(sandbox `e`: `--net-strict=true`; sandbox `f`: `--net-strict=false`; `g`: default open).

Saved shapes: `{"domain":"example.com"}` and `{"domain_suffix":"python.org"}`.

**Strict.** Sandbox `e` (strict true, Silo's value today):

```
curl https://example.com                 -> 000 (SSL_ERROR_SYSCALL)       <- allowed by a hostname rule, still fails
curl https://api.github.com/zen (sandbox h, rule allow@api.github.com:tcp:443, strict) -> 200
sandbox f (strict=false) curl https://example.com -> 200
restore of f's snapshot with the same rules (restore has no --net-strict) -> strict=True, curl https://example.com -> fails
```

Cause, from the runtime source (`crates/network/lib/engine/tls/proxy.rs`) and Silo's patch: Silo's network patch
intercepts TLS only for hosts a secret covers and bypasses all other TLS. With `strict` a bypassed connection
that was admitted only through a hostname rule is denied ("TLS bypass denied by strict hostname policy").
So under strict, hostname rules work only for secret hosts (GitHub). `NetworkBuilder::strict(bool)` and
`msb create --net-strict=false` turn it off; `msb restore` has no such flag.

**With strict=false** (sandbox `f`), from the guest:

```
https://example.com (allowed)                         200
https://example.org (not on the list)                 000
--resolve example.org:443:<example.com's IP>          000   (SNI is checked: no sharing the IP)
https://www.python.org (*.python.org)                 200
https://python.org  (apex of the suffix rule)         301   (the suffix rule covers the apex)
https://pypi.org                                      000
https://1.1.1.1  (direct public IP)                   000;  tcp connect 1.1.1.1:443/:80 -> ConnectionRefused
http://example.com:80 or IP:80                        refused (only 443 listed)
tcp connect to an allowed host's IP:443               succeeds at TCP level; HTTPS to another name via that IP fails
```

**DNS** (UDP/TCP query, python script, from the guest):

```
                         allowlist (e, f)              open (g)
example.com via gateway  answers=2                     answers=2
example.org via gateway  answers=2  <- NOT filtered    answers=2
unknown name via gateway NXDOMAIN                      NXDOMAIN
example.org -> 1.1.1.1   NXDOMAIN (udp and tcp)        answers=2
example.org -> 8.8.8.8   NXDOMAIN                      answers=2
```

A name that is not on the list still resolves through the gateway (so a computer can leak data in query names
until the DNS log/filter exists, which the plan leaves out). Queries sent straight to 1.1.1.1 or 8.8.8.8 get
NXDOMAIN, so the allowlist drops the public resolver as the plan wants (the `allow@public` rule is simply
absent; TCP connects to :53 on any address succeed but are answered by the gateway resolver). Resolving an
allowed name matters: the runtime maps the answer to the name, which is how the IP is admitted.

**TLS-intercepted hosts for secrets** keep working (`api.github.com` 200 under strict). In the patch, a host
is intercepted only while a current secret allows it, so "GitHub's hosts, each assigned secret's hosts" work in
either mode; other hosts are plain pass-through TLS and need `strict=false`.

## 5. `--vsock`

```sh
msb create … --vsock $HOME/.s1/work/v.sock:5000 …       # accepted; inspect shows routes[host_socket, port 5000, stream]
msb start …                                              # ok
# in the guest: socket(AF_VSOCK).connect((2, 5000)) -> banner from the Mac's listener, 5 of 5
# CID 3 and 1 are reset, 0 and 0xFFFFFFFF time out; use CID 2.
msb restore g-v:ckv --name e2e-s1-x --vsock …v.sock:5001   # restore accepts it too and it works
msb restore g-v:ckv --name e2e-s1-w                         # no flag -> the restored computer has no vsock
```

The listener identifies the computer by its socket path, one per computer. Exports refuse a non-empty
`vsock` (`validate_snapshottable_config`) **(read)**, so the engine would reset it like the policy.
It does not exist for macOS VMs or containers.

## 6. macOS computers and containers **(read)**

- `macos-gateway/src/control.rs`: `InitRequest.policy: Option<NetworkPolicy>` (`microsandbox_network::policy`),
  deserialized from the JSON the engine sends (`computer_gateway.rs`, field `policy: Option<&Value>`, "in the
  shape MicroSandbox saves one"). The runtime's own saved policy has the same type, so `group: host` with a port
  and `domain` / `domain_suffix` are accepted. `None` means `NetworkPolicy::from_profiles([Public])`.
- Today the macOS init request (`macos_computers/proxy/supervisor.rs`, `struct InitRequest`) has **no `policy`
  field**, so a macOS computer always gets the gateway's Public default. The container gateway
  (`computer_gateway.rs`, `Params.policy`) can carry one and sends only `blocked_gateway_policy()` for blocked
  containers (`containers/lifecycle.rs:1322`). Nobody sends a host rule yet; macOS needs the field added.
- `host.microsandbox.internal`: defined in `crates/network/lib/lib.rs` (`HOST_ALIAS`) and answered by
  `engine/dns/forwarder.rs` with the gateway addresses. The gateway uses the same forwarder and the guest's
  DNS is the gateway (`dns_ipv4: ipv4.dns.unwrap_or(gateway)`). The macOS guest's DNS configuration is written
  by the network bootstrap files, not checked here.
- `network.rs` builds the config with `NetworkBuilder::new()...policy(policy)` and never calls `.strict(false)`;
  the builder default is `strict: true`. Hostname rules for non-secret hosts will fail there as they do in
  `e`. Fix: pass a `strict` field through the init request and call `.strict(false)` for allowlist computers.
- The gateway takes its policy at init only (plan fact): a policy change applies at the next boot.
- Not run: no live macOS computer.

## 7. The guest program

```sh
cd app/SiloUI
export PATH=$HOME/.zvm/bin:$PATH CARGO_TARGET_DIR=$HOME/code/projects/silo-wt-targets/S1
bash scripts/build-guest-silo.sh
```

- The script wraps `zig cc -target aarch64-linux-musl` as `cc`, `ar` and linker for the target; it ends with
  `cargo build --release -p silo-cli --target aarch64-unknown-linux-musl --locked`. It prints
  `<root>/target/...` even when `CARGO_TARGET_DIR` is set; the binary is
  `$CARGO_TARGET_DIR/aarch64-unknown-linux-musl/release/silo`.
- Result: clean build of 167 crates in **35.7 s**; **12,682,408 bytes**; `ELF 64-bit LSB executable, ARM aarch64,
  statically linked, stripped`. One warning (`libc::time_t` deprecated, `cli/src/clock.rs:99`).
- Without the wrapper (`cargo build -p silo-cli --release --target aarch64-unknown-linux-musl --locked`): fails
  in `ring`'s build script, `aarch64-linux-musl-gcc` missing (through `sccache`).
- Dependencies that force a C compiler: only `ring` 0.17.14 (a build dependency on `cc`), pulled by `rustls`
  and `rustls-webpki`, themselves pulled by `reqwest` in `silo-cli`. Nothing else in the musl graph builds C.
- No `github-build.local.json` was needed (it is only for the native app build).
- In the guest: `msb cp silo e2e-s1-a:/tmp/silo`, then `/tmp/silo --version` prints `silo 0.1.0`, and `--help`
  lists the commands.

## What to build, from this

Channel: `--net-rule allow@host:tcp:<P>` is enough, no patch. Allowlist: hostname rules need `strict=false`;
create can set it, restore and fork cannot (no flag) and the macOS gateway never sets it. That is the one
place a small patch (`restore --net-strict`) or a gateway field is needed. Details are in the report.

## Appendix: the throwaway export test

Appended to `engine/src/backup.rs` for the run and removed afterwards (not committed). Command:
`S1_CFG=<folder of inspect configs> cargo test -p silo-engine --lib s1_export_checks --locked -- --nocapture`.

```rust
mod s1_probe {
    use super::*;
    fn show<T>(r: Result<T, BackupError>) -> String { match r { Ok(_) => "ok".into(), Err(e) => e.to_string() } }
    #[test]
    fn s1_export_checks_on_real_configs() {
        let dir = std::env::var("S1_CFG").unwrap();
        for name in ["q", "o", "p", "a", "i", "e", "h", "f"] {
            let mut config: Value = serde_json::from_str(&std::fs::read_to_string(format!("{dir}/{name}.json")).unwrap()).unwrap();
            let sandbox = config["name"].as_str().unwrap().to_string();
            let before = show(validate_snapshottable_config(&sandbox, &config));
            let exported = show(portable_export_network(&sandbox, &mut config));
            let after = show(validate_snapshottable_config(&sandbox, &config));
            println!("S1 {name}: live {before} / export {exported} / after reset {after}");
        }
    }
}
```
