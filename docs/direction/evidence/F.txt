[FAIL] R12-a The app did NOT start its own engine with nothing done by hand. After `open` the app showed "Silo could not load: Silo's engine is not reachable yet" and the Dev job stayed broken for 4+ minutes (runs 3, 4, 5 ... 18).
       `launchctl print gui/501/org.silo.dev.engine` (real output, f-launchctl-1.txt / f-launchctl-before-bootout.txt):
         path = (submitted by smd.30659)   type = Submitted   managed_by = com.apple.xpc.ServiceManagement
         state = spawn scheduled           job state = spawn failed
         program identifier = Contents/Resources/SiloEngineDistribution/Silo Engine.app/Contents/MacOS/silo d (mode: 2)   [relative path]
         parent bundle identifier = org.silo.dev   parent bundle version = 0.13.0   BTM uuid = D663F80F-...
         runs = 18   last exit code = 78: EX_CONFIG   (first print: last exit reason = OS_REASON_CODESIGNING)
       Cause: the R12 parser does not read this format. app/SiloUI/src-tauri/src/engine_client/launcher.rs JobDetails::parse (line ~78):
         - it looks for the key "program", the real key is "program identifier" (value ends in " (mode: 2)"), so details.program is never set;
         - "last exit code" is parsed with value.parse::<i32>(), but the real value is "78: EX_CONFIG", so last_exit_code is always None
           (while running it reads "(never exited)", also None); the EXIT_CONFIG (78) test in stale_reason therefore never fires;
         - "state = spawn scheduled" is read correctly (running false) and the "pid = N" line only exists while running.
       So stale_reason() returns None, the launcher falls to `self.service.start()` (kickstart) forever, as in M/A1. Fix: parse the leading integer of "last exit code" ("78: EX_CONFIG" -> 78) and read "program identifier" (strip " (mode: N)"); the unit test used a shortened sample.
       Workaround (not by the app): `launchctl bootout gui/501/org.silo.dev.engine` (Dev label only), then Retry in the app: the app registered its own job and the engine came up (pid 39566, runs = 1, state running, "last exit code = (never exited)").
       Also seen: when the job is removed (bootout) while the app is OPEN, the app registered a fresh job within seconds, no Retry; and with the app closed, `open` of the app after a bootout registers and starts the engine in about 10 s (twice). So the missing-job path works; only the stale-job path fails.
