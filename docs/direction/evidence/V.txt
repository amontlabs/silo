== FINDINGS (bugs and oddities; no product code changed in this task)
1. Environment, not product: LCU `getApp("Silo Dev")` / bundle id resolved to another copy (microsandbox-workspaces/.../release/bundle) and launched it on every call; the running copy answered each launch with "Silo Dev is already running. Quit it first" (src-tauri/src/single_instance.rs). `lsregister -f` on the direction bundle fixed the resolution. Several copies of org.silo.dev exist (main checkout release build, two t3 worktrees).
2. The Dev app does not start the Dev engine in this setup: "Silo could not load: Silo's engine is not reachable yet" until the bundle's silod was started by hand (as t5b_tools_check.sh does). After it ran, Retry loaded the app, but a red "System issue: Silo runtime is unavailable ... desktop bridge did not respond" kept every Open Terminal / Claude Code / Codex / Zed / Stop button disabled ("Resolve the system issue first.") until "Retry checks" was clicked. Worth checking whether the app should retry its own checks when the engine appears (src/features/application/model/computer-availability.ts).
3. Every fork reports a conflict on /etc/silo/endpoint.json ("changed on main since the fork was made, and differently in the fork; fork: added; main: added"), so each merge of a fork needs --choose file:/etc/silo/endpoint.json=fork (or the app's radio). The file is per-computer; it should be left out of the diff/merge (engine changes ignore list; guest_client / changes code).
4. A merge approval shows as two Pending rows and the badge counts both: "e2e-v-main asks: Merge ..." and "e2e-v-g2 into e2e-v-main -- No changes -- Open" ("2 waiting for you" for one ask). The request row says "No changes" (`silo requests`: "no changes counted") although the diff has 2 settings changes; a request made with `--request` counts them ("settings 2").
5. The review page opened from a merge approval shows the target as an id ("e2e-v-g1 -> 358726eb-e1a8-...", "Merge into 358726eb-...?") where the same page from a `--request` shows names; the conflict text uses ids and CLI words ("Merge again with `choices`: ... Add an id to `skip` ...", "Keeping ab4fafba-..."). The approval carried "Choices: endpoint.json = fork", yet merging from that page asked for the choice again (the approval itself had expired by then; not separated).
6. Failed install: the button after the error is still "Install Codex" (checklist says Retry) and the error is generic ("The runtime did not complete the operation"); a blocked network is the likely cause and could be named.
7. Clicking "Pending" in the sidebar while a request's page is open leaves that page; Back is needed to reach the list. A toast "Couldn't delete e2e-v-f2" (from my CLI drop of a running computer) stayed on screen for the whole session.
8. Activity > Who did what > "Open request" did nothing on a row of a removed computer (src/features/application/components/audit-log.tsx:42, onOpenApproval). Either it should be hidden/disabled there or the request page should open.
9. Inside a computer `silo tools status <computer>` is refused with an internal name in the message (guestClient.status); `silo tools --help`/docs should say agents cannot ask, or allow a read-only status.
10. On e2e-v-main right after the installs the "Silo's tools" row read "Claude Code and Codex not installed yet" while Agents said Ready (seen once, may be stale until refresh).
11. Disk: the run took about 41 GB at its peak (113 GB free at the start, 73 GB with all computers running); 96 GB free after cleanup (the rebuilt/installed images and caches stay). The create form's defaults are 8 CPUs / 32 GiB / 120 GiB + 100 GiB disks.
12. Notifications: the "Enable notifications" switch becomes disabled and stays off while the macOS permission banner is up and unanswered.
