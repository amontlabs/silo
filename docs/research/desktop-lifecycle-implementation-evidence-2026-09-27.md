# Detached Linux desktop viewer: implementation evidence

Date: 2026-09-27
Scope: proposed lifecycle and integration for the existing optional Ubuntu guest desktop, keeping Xfce/X11 apps alive when a native Selkies 2 viewer or its SSH tunnel disconnects. This is an evidence note, not an implementation or a reliability claim. Repository facts below were inspected at the current worktree; upstream feature claims link to primary project documentation.

## Recommendation

Use the existing guest `silo-desktop` lifecycle and existing native Tauri viewer, replacing the coupled KasmVNC display with `Xvfb :1` + the existing Xfce startup + a separately launched Selkies 2.0.0 server attached to `:1`. Keep the WebSocket transport and reuse Silo’s existing per-viewer SSH tunnel and authenticated loopback proxy. Do not use `selkies-session`: it owns Xvfb, audio, desktop, and Selkies as one session and stops those child processes when it exits, which does not provide the requested independent viewer/server lifetime. Selkies’ native package explicitly attaches to an existing X.Org display and PulseAudio or PipeWire-Pulse server, and installs without starting a session ([native install docs](https://github.com/selkies-project/selkies/blob/2.0.0/docs/native.md), [2.0.0 release](https://github.com/selkies-project/selkies/releases/tag/2.0.0)).

This is the smallest architecture that preserves the product’s existing guest-control API, remote SSH path, and attach/detach UI behavior. Extend the current supervisor to own the independent Xvfb/Xfce session and Selkies in separate process groups; do not add a second supervisor, desktop manager, lease, queue, or input arbitration. Human and agent input can continue concurrently in the same X11 session, as they do today.

The current local VM shutdown behavior is owned by the existing runtime, not the viewer. Closing a viewer drops only its host tunnel and proxy. Stopping/Quitting Silo shuts down Silo-owned local VMs, which destroys their in-guest desktop process state; the local app does not stop remote VMs. A viewer migration must not change this lifecycle contract. On a guest reboot, Xvfb and the session start fresh; a connection that succeeds after reboot does not mean the prior application processes survived. Application restart/recovery is a separate application-level behavior and is not established here.

## Proposed process model

1. Keep `silo-desktop` as the single root lifecycle entry point and its current `/run/silo-desktop` runtime state. Under its existing lock, have it create/validate a per-session XDG runtime directory, launch `Xvfb :1` as `silo` with the chosen fixed framebuffer size and required X extensions, then launch DBus/Xfce with `DISPLAY=:1` and the matching PulseAudio-compatible environment. Start Selkies as a separate child process with the same display/runtime/audio variables and `--addr=127.0.0.1 --port=6901` with the existing upstream Basic credentials. The active SSH route targets guest loopback; confirm this with the real local and remote connection during qualification.
2. Use Selkies’ default WebSocket mode. Its 2.0.0 release documents one TCP port for video, audio, input, clipboard, and file transfer; WebRTC is opt-in and would add ICE/TURN and UDP reachability concerns without helping the existing SSH-forwarded viewer. Native docs support loopback binding for SSH forwarding, matching the active Silo viewer route; validate this on both local and remote owners ([release](https://github.com/selkies-project/selkies/releases/tag/2.0.0), [native install](https://github.com/selkies-project/selkies/blob/2.0.0/docs/native.md)).
3. Keep the lifecycle relation explicit: viewer loss/reconnect affects only `src/desktop_viewer.rs`’s proxy and tunnel; a Selkies process restart affects only the stream endpoint; Xfce application state is preserved while Xvfb/Xfce remain alive. A deliberate guest desktop stop, VM stop, or VM reboot still ends those applications. Retain the existing desktop action names and status schema where practical so Silo UI and remote dispatch remain stable; expose backend/product/schema details only as needed for migration and diagnostics.
4. Do not invoke Selkies’ `selkies-session` wrapper in this topology. Upstream documents that wrapper as starting sound server, Xvfb, desktop, and Selkies together and stopping the session’s children on termination. It is the right standalone-session adapter, but it couples exactly the lifecycle that this Silo request separates.

`Xvfb` and the display session must start once per guest desktop lifecycle, not once per viewer. Keep the current fixed `:1` contract initially: Luda and other session tools already target it, and a dynamic display would widen this change across lifecycle, readiness, agent environment, and X socket validation. Reimplement stale-display cleanup for Xvfb only after proving process/socket ownership and liveness; do not carry over Kasm-specific assumptions such as port 5901 or `vncserver -kill`.

## Safe migration from a live Kasm desktop

KasmVNC currently owns both the X server and Xfce applications attached to that server. Those app processes cannot be transparently moved from the old X server to a new Xvfb. Therefore an in-place backend swap cannot preserve running windows or unsaved application memory. Preserve the user’s home and application files; make no claim that a stopped live session can be restored.

Use an explicit, versioned guest migration operation rather than changing the behavior of `setup-tools`, `configure_with()`, or a boot hook:

1. **Inventory and stage:** retain KasmVNC 1.5.0, its config, credentials, current installed marker, package receipt, and existing `/home/silo` unchanged. Download the exact Selkies 2.0.0 Ubuntu 24.04 package for both `amd64` and `arm64`, verify a source-published checksum before installing, and install `xvfb` plus required audio packages. The upstream release/docs establish Ubuntu 24.04 packages for `x86_64` and `aarch64`; the release’s exposed asset list did not show the Ubuntu 24.04 filenames or checksums during this review, so retrieve and pin the exact asset hashes from the release API/source before implementation. Do not substitute a floating `latest` asset. Stage test the new stack on an alternate display and port while leaving `:1` and all current applications running; this validates package and viewer wiring, not migration of the old session.
2. **Cut over explicitly:** only when the user chooses the migration action, stop the current Kasm process through the existing supervisor, recording the expected session loss. Do not introduce agent/human coordination or input leases. Keep existing `connection.json` username/password if Selkies accepts them; otherwise rotate using the already private root-owned file and ensure the proxy fetch path handles the same schema. Back up only root-managed config/receipt state, not application data.
3. **Start and verify:** start Xvfb `:1`, Xfce/DBus, audio service, and Selkies separately, then verify X socket/process ownership, port 6901 readiness, HTTP/WebSocket handshake, screenshot, keyboard/pointer input, clipboard in both directions, file transfer, audio, resize/HiDPI, and reconnect after closing the viewer. Test VM reboot separately and describe it as a fresh desktop session. Do not infer it preserves old processes or unsaved state.
4. **Rollback:** on failed verification, stop only the new Selkies/Xfce/Xvfb process group and restart the retained Kasm backend. This returns a working fresh desktop, not the ended Kasm application processes. Keep Kasm packages/config until the Selkies path passes the release gate; then remove only the pinned Kasm package and managed config. Failed attempts must leave the old package and receipt available for another explicit retry.

Version the guest receipt with a schema and backend identity (for example `schemaVersion`, `backend: selkies`, `backendVersion`, `xServer: xvfb`, package hashes, and config digest). Keep a separate migration phase/receipt so ordinary `status`, `start`, app boot, and `setup-tools` cannot silently change a version-1 Kasm install. New desktops can install the new backend directly. Existing version-1 installations remain Kasm until the explicit migration action succeeds. Continue to use the existing service protocol probe in `desktop.rs`; bump it only if the host/guest JSON contract actually changes. Current `installed.json` uses a version-1 receipt and current guest `status()` hardcodes `version='1'`, so both need a deliberate compatibility decision before the update.

## Host changes if implemented

Keep Rust desktop action routing, remote transport, `desktop_endpoint()` port 6901, viewer window behavior, and Linux desktop UI model. Update only proven Kasm-specific points:

- In `guest/setup-desktop.sh`, replace pinned Kasm acquisition with pinned Selkies package acquisition for the two guest architectures; add `xvfb` and the required audio server packages, record license/NOTICE inputs, and write a backend/schema receipt. Preserve optional Luda provisioning and installation state as a distinct step.
- In `guest/desktop-service.py`, make the existing supervisor manage Xvfb/Xfce and Selkies separately with bounded readiness checks; replace `vncserver`, Kasm ports/process names, and stale-display logic. Keep port 6901, user `silo`, the private credential file, and app-specific working account checks. Do not add another supervisor.
- In `src/desktop_viewer.rs`, replace Kasm-specific URL settings (`resize=scale`, `clipboard_seamless=false`) with verified Selkies client options; retain the private host cookie and tunnel lifecycle. Selkies exposes capability switches for clipboard and file transfer, so explicitly configure Silo’s intended policy rather than assuming Kasm defaults carry across.
- In `src/desktop_proxy.rs`, preserve native-cookie validation and Basic Auth injection if Selkies’ same-origin WebSocket path fits. Test and adjust allowlisted methods/headers/body size against the 2.0.0 client’s actual file and clipboard routes; the existing proxy accepts GET/POST/HEAD and caps request bodies at 64 MiB. Keep the proxy loopback-only and guest service off public host interfaces.
- Update desktop docs/help, `THIRD-PARTY-NOTICES.md`, release packaging/licensing notes, and add a user-visible `silo-ui` changeset when behavior ships. The app embeds guest source using `include_str!` in `desktop.rs`; no new host binary bundle is required if the pinned guest `.deb` remains fetched and hash-verified in the guest installer. Release tests should cover exact Selkies package hash per architecture and preserve the current supported host package matrix (macOS 14+ Apple Silicon, Linux Ubuntu 24.04-compatible x86_64/ARM64), while desktop-specific integration remains gated on Ubuntu 24.04 guests; Linux execution hosts require KVM, while macOS uses its existing VM backend.

This proposal adds Selkies only inside the Linux guest. macOS/Linux app hosts still use the existing native Tauri webview and SSH path; there is no Selkies host daemon on either app host. The candidate native `.deb` files and Selkies server are Linux-only. Upstream release metadata lists `x86_64` and `aarch64` Ubuntu 24.04 assets; this is a platform-support claim, not performance or reliability evidence on Silo’s VM configuration.

## WebView and feature unknowns to close before implementation

The upstream client uses WebCodecs and a bundled web client, and its release notes document clipboard controls, real RandR outputs for multi-display pages, and X11 resize/scale support. That does not prove that Tauri’s WKWebView on macOS 14+, or WebKitGTK on supported Linux, implements every codec, clipboard event, fullscreen input, or monitor behavior the same way as the tested browsers. Keep the candidate at one desktop surface initially; verify WebCodecs H.264 support and software fallback on both hosts, key mappings/IME, HiDPI, and resize before advertising support. Multi-monitor and file transfer should be enabled only after the native webviews and Silo proxy pass real integration checks. No performance or reliability result was measured for this candidate.

Selkies’ own docs list clipboard, files, audio, camera/microphone, input, and resize capability switches. This is a same-VM trusted desktop shared by the Silo user and agent tools, so set per-VM product policy explicitly. The proposal does not disable every channel by default: clipboard and file transfer are product functions to exercise and decide from this trust boundary, not an assumed global security setting. Do not enable WebRTC/TURN for the existing SSH path.

## Dependencies, licenses, and related Luda/LCU work

Selkies 2.0.0 is published under MPL-2.0 in its [`pyproject.toml`](https://github.com/selkies-project/selkies/blob/2.0.0/pyproject.toml). Its upstream development guide says modified MPL source files distributed externally must be made available, while separately originated dependencies may have more restrictive terms ([development and contributions](https://github.com/selkies-project/selkies/blob/2.0.0/docs/development.md)). The native docs say its package carries `pixelflux`, `pcmflux`, interposers, and Python dependencies in a private `/opt/selkies` environment while obtaining system libraries through the guest package manager. Before distribution, inventory notices and codec build variants for the actual `.deb` (including its H.264 software encoder path); do not infer package-wide obligations solely from the top-level license. Silo’s current [`THIRD-PARTY-NOTICES.md`](../../app/SiloUI/THIRD-PARTY-NOTICES.md) has no Selkies receipt today.

Keep current Luda 0.3.4 pinned and preserve its state during this transport/display migration. Treat LCU as a separate guest-readiness and packaging phase, with its own hash-pinned release, permission review, runtime dependencies, and verification. The official [LCU 0.4.0 release](https://github.com/0xpolarzero/lcu/releases/tag/v0.4.0) dated 2026-09-27 supports Linux ARM64/x86-64 but requires the official ChatGPT Linux app installed first and stores a private managed copy; its archives contain no OpenAI application binary. Do not silently replace the current Luda pin with LCU 0.2.1 or another version, and do not bundle or fetch the ChatGPT application through Silo.
