# Silo 0.13.0

### Opening this version

If you install from the DMG: this build is not signed with an Apple Developer ID or notarized, so the first time you open Silo, macOS says it cannot verify the app. Open System Settings → Privacy & Security and click **Open Anyway** next to the message about Silo, or run `xattr -dr com.apple.quarantine /Applications/Silo.app` after copying Silo to Applications. You only need to do this once. After an in-app update, macOS may ask again for Keychain access or for permissions you granted before, because each build of an unsigned app has a different signature; this has not yet been checked on a real update.

### Minor Changes

- f220bc5: `.silo/silo.yaml` takes per-agent overrides under `agents:` (recipes, fork secrets, fold, auto-keep rules and step checkpoints), chosen by `--agent`, `SILO_AGENT` or the MCP client's name. A keep that brings packages or settings files appends them to the recipe the computer came from (`--no-write-back` skips it), and `silo fold <fork> --pr` pushes a fork's code to a new branch and opens a pull request with the review summary.
- f220bc5: `auto_keep:` rules in `.silo/silo.yaml` (and `fold: auto-code`) keep a fork's changes without asking when every change is in the buckets a rule lists and, if the rule asks, the recipe's `test:` command passes in the fork. They apply to `silo fold --request` and at the end of `silo fork ... -- cmd`; anything else, and any fork with uncovered database changes, left-behind credentials or a stale review, gets a review request.
- ed46c09: An agent can drive a fork's desktop from the host: `silo mcp` has screenshot, click, type, key, scroll, move, drag and wait tools for a computer, `silo fork --gui` (or the `fork_gui` tool) forks, starts and waits until the desktop and computer-use driver are ready, and `--computer-use auto` sets a fork's approval for the agents inside it to no prompts (forks only; `main` keeps its mode). The host tools drive forks and refuse `main`. Computer-use files no longer show up as changes in a fork's review, and `silo status` shows a computer's computer-use approval.
- f220bc5: `silo status` and `silo diff` now show which Silo-managed secrets a fork used, per host and method (and attempts the GitHub profile refused), for Linux and macOS computers. The new engine method `computers.credentials` reads the events the network proxy records; they hold names, hosts and methods, never values.
- ed46c09: Pro: `silo review <fork|request>` (and `silo requests show --review`, and the MCP `review` tool) sends a fork's diff (and, for the code lens, a redacted text of its code changes) to a hosted reviewer you configure with `SILO_REVIEWER_URL` or `~/.config/silo/reviewer.yaml`, and shows general, packages and code findings under an advisory note. It is off until configured. The service is in `reviewer-service/`.
- ed46c09: An agent living inside a Linux computer can now fork it and ask for review from inside with `silo --in-guest`. `silo guest-client install <computer>` gives the computer a token the engine checks on every call: the agent can fork itself, diff its forks and ask for review, and cannot keep, promote, undo, drop or change secrets, whatever its `fold` setting. Promote and undo revoke the tokens of the computers they swap.
- cb75b2e: A fork's changes can be kept into the computer it came from with `silo fold`, and put back with `silo undo`. A keep first saves a checkpoint of the computer, stops without changing anything when the fork and the computer changed the same thing or when a database change has no migration, replays packages by name and version, merges git, copies files, merges crontabs and launch agents, and runs the recipe's migrate, restart and after steps. Works for Linux and macOS computers.
- 2382ccc: Make this main now carries main's SSH entry, proxy certificate authority and hostname (macOS) to the new main, puts the fork's parked scheduled jobs back, and keeps forks of the old main pointing at whichever computer is main. `silo undo` takes back the newest of a promote and a keep, undoes only the latest promote of a computer, and refuses when the computers were renamed since rather than leave two named main. Ports changed while the fork was main stay with the main role when undone. An interrupted promote holds both computers until it is settled at start.
- 2382ccc: `silo fold <fork> --promote` now works for Linux computers. The bundled runtime can rename a stopped computer, so the fork takes main's name and published ports, main is kept stopped as `main-before-<time>`, saved SSH entries follow, and the fork's parked scheduled jobs are put back through the guest. `silo undo main` swaps them back.
- 2382ccc: `silo fold <fork> --promote` makes a fork the main computer: it takes main's name, published ports, secrets and GitHub access, and the old main is kept stopped as `main-before-<time>`. `silo undo main` swaps them back. Available on macOS computers; the fold tool in the MCP server takes `promote` too.
- 889290b: A Pending changes screen lists the review requests of this device and every connected device, and opens one to review its changes, keep it, throw it away or open the fork. A computer's Checkpoints tab lists the steps run in it and can fork a new computer from a step.
- 21e00ba: Linux forks now start quiet: they cold-boot the disk only, get a new machine id and hostname, have scheduled jobs turned off, and receive no secrets or GitHub access unless you name them. GitHub access copied to a fork is read-only. A fork can also be told which programs to stop and which files to delete.
- 21e00ba: Forks of a Mac computer now start quiet: the source's scheduled jobs, crontabs and scheduled launch agents are moved aside (services that keep running stay) before the fork first starts, the processes and paths a recipe names are stopped and deleted, and no secret or GitHub access is copied unless it is named. Forking a Mac without choosing a checkpoint now forks its current state from a "Fork point" checkpoint that stays while a fork made from it exists. A Mac fork that has not started yet is also no longer broken by Retry setup, and its first start now stops when you stop it.
- 2382ccc: Recipes: describe a clean computer in `.silo/recipes/<name>.yaml` (OS, packages, setup commands, services, ports), build it once with `silo recipe build`, and fork from it with `silo fork <name> --recipe <recipe>`. `silo up` makes `main` from a recipe, starts it and keeps a warm checkpoint, so forks of an unchanged `main` start from that checkpoint instead of building `main` again. `linux-dev` and `macos-xcode` come built in.
- 2382ccc: A fork of main now starts from its warm checkpoint only if the engine can tell main has not changed since it was taken (the engine tracks a per-computer generation that commands, file writes, keep, restore and similar operations move) and it is under a minute old (`warm_max_age` in `.silo/silo.yaml`; changes made over a plain `ssh` session are not seen), and says which checkpoint it used. Recipe builds no longer collide, keep the previous build until the new one succeeds, and run their services under the service's own name.
- ed46c09: Drive another Mac's computers from this one over Connections: `silo --device <name>` runs fork, diff, fold, requests, steps and tree on that device, `silo list --all-devices` and `silo requests --all-devices` give one list across devices (a device that cannot be reached is reported, not fatal), and a request is kept, thrown away or opened on the device it is on. The MCP tools take `device` and `allDevices`.
- fae429a: Resident agents: the built-in `openclaw` and `hermes` recipes install the agent in `main`, start its gateway as a service, and list the gateway under `quiet:` and its token file under `scrub:`, so a fork of `main` does not answer the same chat channels twice. Use them with `silo up --recipe openclaw`, then `ssh main.silo` and `silo guest-client install`.
- f220bc5: Review requests can now be listed, shown, kept, thrown away and opened with `silo requests` and the matching MCP tools. A request shows a fresh diff of its fork and a "Credentials used" line, a keep is pinned to the changes the request was made from, and throwing a request away never drops main or the computer the changes would be kept into.
- 21e00ba: Added the `silo` command line and an MCP server (`silo mcp`) to list, create, start, stop, fork, drop and run commands in computers, and to save checkpoints. Projects can describe forks in `.silo/recipe.yaml` and `.silo/silo.yaml`.
- fae429a: The app now carries the `silo` command and links it into `~/.local/bin` every time Silo starts (`silo-dev` for Silo Dev), so the command line and MCP server need no separate build. Silo replaces only its own earlier link; a `silo` file or link of your own is left alone and Connections shows that the command is not on PATH.
- cb75b2e: Add `silo diff <computer>` and a `diff` MCP tool to show what changed in a fork since it was forked: code, packages, settings and files, databases and the rest. `silo fork` now records the fork's starting state for the comparison.
- 2382ccc: `silo fork -n N` makes several forks at once (capped by `fork_ram_budget` and Apple's two macOS VMs), `silo fork <source> -- <cmd>` runs a command in the fork, `silo fork ./repo` copies a git repository into a fresh Linux fork and `silo fold` brings only its commits back (with `silo undo` to go back), and `silo fold --request` records a review request in the engine.
- f220bc5: Silo records the commands an agent runs on a computer as numbered steps (`silo steps`), can save a checkpoint after each one (`step_checkpoints` in the project settings), forks from any step (`silo fork --from-step N`), and shows how computers descend from each other with `silo tree`.
- 21e00ba: Each computer's published websites now open at their own local name, such as `http://3000.my-computer.silo.localhost:47383`, so several computers serving the same port can be opened side by side.

### Patch Changes

- 25ca53e: Deleting a computer now also removes its empty checkpoint folder, and checkpoints taken before Keep are trimmed oldest first within a chain.
- 25ca53e: Deleting old checkpoints and compacting a computer's disk now give the disk space back; each saved checkpoint no longer keeps an extra set of its disk layers for as long as the computer exists.
- 889290b: Review requests no longer stay open after their fork is deleted. Deleting a computer closes the open requests that name it as the fork or the target, `silo requests` shows them as "closed: fork deleted" or "closed: target deleted", and the list closes any left over once it can see every computer. Forking from a step now closes the fork popover instead of reporting that the new computer's name is taken.
- 25ca53e: A fork now starts from the checkpoint's disks instead of resuming its memory, and the memory files a restore leaves behind are removed once no checkpoint uses them. Freeing checkpoint disk on a computer with large disks now waits for the merge to finish instead of failing and leaving the next checkpoint to fail.
- 2382ccc: Forks made with `silo fork -n` publish the same ports as their source and print their URLs. `silo fold --promote` waits for both computers to finish stopping, `silo undo` of a promote starts the computers that were running before it, and folding a stopped folder fork starts it for the fold and stops it again.
- ed46c09: Fixes for the in-guest client: `silo guest-client install --binary` now uploads the binary before it creates a token, so a failed upload leaves no token. Non-root users in a computer can reach the bridge. Forking or promoting a running computer no longer fails after its agent has called the bridge. Every fork drops the guest-client token file it copied from its parent. Promoting a computer whose name is longer than 11 characters now works.
- cb75b2e: A keep is no longer refused because of background changes on the fork or on main that the keep does not read or write.
- 21e00ba: A new macOS computer gets its own password again, and a disk that cannot be expanded no longer leaves the computer unfinished: it is ready to start and shows a note. `silo retry-setup` finishes the setup of a computer that stopped early.
- 21e00ba: Forking a macOS checkpoint boots the fork once: the fork gets its own password and identity while stopped, its first Start is its only boot, and it no longer reinstalls developer tools the checkpoint already had.
- cb75b2e: The change review puts launch agents, crontabs and named files before directory counts, treats macOS background churn as noise, reuses an idle baseline across forks of the same computer, keeps one review digest between looks, and no longer refuses a dry-run keep on an old digest.
- 2382ccc: Making a fork main no longer fails with an ordering error. `silo` can list, publish and unpublish a computer's ports, forks publish the ports of their source, and `silo up` makes `ssh main.silo` work.
- fae429a: A recipe's `quiet:` entry that names one of its `services:` now also stops that service's running process in a fork (for `python3 /opt/app/poller.py`, the `poller.py` process), not only its start-at-boot entry.
- 21e00ba: A fork recipe's `quiet` list now also turns off desktop autostart entries and user services on Linux, and LaunchAgents and LaunchDaemons on macOS, that start the named program, and `silo status --json` shows the boot count of a macOS fork.
- 25ca53e: Computer lists and status reads no longer fail while another computer change is running; they show the last known state with changing computers marked as updating.
